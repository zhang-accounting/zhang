## 账户指令概述

账户指令在张记账中扮演着基础角色，允许用户定义和管理各种财务交易账户。本节深入探讨账户指令的使用方法，并提供示例来说明在不同场景下的应用。

### 定义账户

要定义一个账户，请使用以下语法：

```zhang
{DATE} open {ACCOUNT_NAME} {COMMODITY1} {COMMODITY2}
```

`open` 指令用于启动一个账户，指定它处理的商品。以下是您可以通过元配置指定的额外细节：

- `alias`：为显示目的分配更具描述性的名称。
- `booking_method`：指定用于处理复杂投资场景的方法。支持 `STRICT`, `FIFO`, `LIFO`。`AVERAGE`, `AVERAGE_ONLY`, `NONE` 暂未实现：使用它们（或填写无效的值）会在该 `open` 指令上报错，账户改用账本默认的预订方法（`default_booking_method`，默认 `FIFO`），账本仍可正常加载。
  - `STRICT`：Beancount 的默认方法。减仓必须只匹配一个批次，或一次性减掉所有匹配批次的全部数量；否则报告 `AmbiguousLotMatch` 错误，并在匹配批次中按 `FIFO` 记账。
  - `FIFO` / `LIFO`：在匹配批次中先减取得日期最早 / 最晚的批次。批次的取得日期是成本中写的日期，否则为建仓交易的日期。
  - 与 Beancount 相同，减仓时成本中未写的部分视为通配：`{100 USD}` 匹配所有成本为 100 USD 的批次（不论取得日期），`{100 USD, 2024-01-01}` 只匹配该日取得的批次，`{}` 匹配所有带成本的批次。

#### 预订方法

预订方法对于涉及投资的账户至关重要，影响交易的记录和报告方式。Beancount 用户可以在账户定义中的商品后直接使用双引号定义预订方法，如下所示：

```beancount
1970-01-01 open Assets:Card CNY "NONE"
```

### 账户使用示例

#### 示例 1：开设储蓄账户

```zhang
2023-01-01 open Assets:Savings USD
```

此示例展示了如何开设一个处理 USD 的储蓄账户。

#### 示例 2：定义投资账户并使用别名

```zhang
2023-01-01 open Investments:Stocks USD
  alias: "Tech Stocks"
  booking_method: "FIFO"
```

在这里，创建了一个股票投资账户，使用别名便于识别，并采用 FIFO 预订方法管理股票交易。

### 元配置解释

元配置为账户提供了额外的自定义选项，增强了其功能和报告能力。理解这些配置可以实现更精确的账户管理和报告。

- `alias`：为账户提供易于理解的名称，便于报告和跟踪。
- `booking_method`：决定交易处理方式，对于投资和交易账户尤为重要。

通过有效利用账户指令和元配置，用户可以根据自己的特定财务跟踪和报告需求定制张记账。

## 余额断言与填充

### 余额断言

`balance` 指令断言一个账户持有某种商品的数量：

```zhang
2024-01-31 balance Assets:Bank:Checking 1520.00 CNY
2024-01-31 balance Assets:Bank:Checking 1520.00 ~ 0.01 CNY
```

- 断言在其日期开始时检查，比较的是该账户在它之前所有分录的合计。同一天的交易排在断言之后，与 Beancount 相同。在张记账账本中，写了时间的断言在该时间检查；在 Beancount 账本中，张记账与 Beancount 一样忽略它的 `time` 元数据。如果该账户当天在这个时间之前有交易（早期版本的张记账会把它们计入），这条断言会报告为 `BalanceTimeIgnored` 警告。
- 它涵盖账户及其所有子账户，与 Beancount 相同：`Assets:Bank:Checking` 持有 60 CNY、`Assets:Bank:Savings` 持有 40 CNY 时，`balance Assets:Bank 100 CNY` 成立。
- **断言必须精确相等。**`1520.00 CNY` 只有在余额正好是 1520 CNY 时才成立。只有用 `~` 明确写出的容差才允许差额：`1520.00 ~ 0.01 CNY` 在余额为 1519.99 到 1520.01 之间时都成立。张记账从不推断容差，既不从金额的小数位数推断，也不从任何选项推断。
- 断言只做检查。无论成立与否，它都不会改变任何余额：账户的余额始终是它所有分录的合计，所有余额、报表和日记账显示的都是这个合计。不成立的断言会报告为 `AccountBalanceCheckError` 错误。
- 日记账列出每一条断言，以及断言的金额、检查时的实际余额和是否成立。

:::caution[与 Beancount 的差异]
对于没有 `~` 的断言，Beancount 会根据金额的小数位数推断容差：在 Beancount 中，`balance ... 1520.00 CNY` 在余额为 1519.99 到 1520.01 之间时都成立（最后一位小数的一个单位，再乘以 `tolerance_multiplier` 选项）。张记账不会这样做，因此一个只是因为这种推断的容差才通过 `bean-check` 的 Beancount 账本，在张记账中会报告该断言不成立。修正方法是写出账户实际持有的精确金额，或者用 `~` 明确给出你接受的容差。
:::

### 填充

需要有意地修正余额时，可以从另一个账户为该账户填充。`pad` 指令与 Beancount 相同，为该账户之后的余额断言填充；`balance ... with pad` 为它自己的断言填充：

```zhang
2024-01-01 pad Assets:Bank:Checking Equity:Opening-Balances
2024-02-01 balance Assets:Bank:Checking 1000.00 CNY

2024-03-01 balance Assets:Bank:Savings 500.00 CNY with pad Equity:Opening-Balances
```

张记账会添加一笔补齐交易（标记为 `P`），从填充账户转入断言金额与账户在断言处余额之间的差额，使断言成立。差额从该账户及其子账户分录的合计算起，并计入在此之前已补齐的每条断言的补齐：之前的断言，即使不成立，也不计入。补齐金额记入被断言的账户本身，即使它是父账户。填充总是使账户精确等于断言金额：即使差额在明确写出的 `~` 容差之内也会填充，而 Beancount 此时不填充。账户已经等于断言金额时，不会添加补齐交易。

- `pad` 为该账户本身每种商品在 `pad` 之后某一天的第一条 `balance` 补齐，直到该账户之后的下一条 `pad`。比较的是日期而不是时间，因为 Beancount 没有时间。
- 与 `pad` 同一天的 `balance` 排在它之前（Beancount 对同一天的排序也是如此），不会被补齐，无论它们的时间如何：在带有时间的张记账账本中，`pad` 排在当天最后一条余额断言之后。在 Beancount 账本中，张记账与 Beancount 一样忽略 `pad` 的 `time` 元数据，同一天的 `pad` 保持它们的行序。
- 它的补齐交易使用 `pad` 的日期，紧跟在 `pad` 之后，与 Beancount 相同，因此 `pad` 与断言之间的余额已经包含这笔补齐。当 `pad` 排在当天一条更晚的余额断言之后时，补齐交易的时间是那条断言的时间。
- 填充金额在它所服务的断言出现时计算。日期更早、但服务于更晚断言的 `pad` 的补齐不计入：当子账户的 `pad` 排在父账户的 `pad` 之前、却服务于更晚的余额断言时，父账户的填充不计入它，父账户的断言会差出这部分补齐而不成立，与 Beancount 相同。
- `pad` 和它所服务的 `balance` 可以在账本的不同文件中。
- 没有填充任何金额的 `pad`（之后没有该账户的断言需要它）会报告为 `UnusedPad` 错误，与 Beancount 相同。
- `balance ... with pad` 为它自己的断言填充，日期是它自己的日期，不会被报告为未使用。它之前的 `pad` 会先为它补齐。
- 如果填充的商品在该账户或其子账户中按成本持有，会在断言上报告 `PadWithCost` 错误，与 Beancount 相同。补齐交易仍然记账，但不带成本。

`balance ... with pad` 仍然是一条断言，与其他断言一起列在日记账中。它在同一时间的所有余额条目记账之后才检查；当补齐无法使合计达到断言金额时，它会报告 `AccountBalanceCheckError` 错误，而不会悄悄地不成立：

- 同一时间子账户的填充随后改变了合计。请先写子账户的余额，再写父账户的余额；批量对账工具会这样做；
- 它从被断言的账户本身或其子账户填充：这样的补齐只是在它所断言的合计内部转移金额，永远不会改变合计。Beancount 中这样的填充同样不成立。

在 Beancount 账本中，通过界面或批量对账工具创建的余额断言会这样写入，使 Beancount 与张记账的理解一致，并且只在你要求的时候、只补齐你要求的金额：

- “我现在的余额”写成日期为明天的 `balance`，它排在今天所有交易之后。今天之后再添加的交易不在你断言的金额中，因此会使这条余额断言不成立，与 Beancount 相同：请重新核对余额。
- 带填充时，你填写的金额与该账户及其子账户当前持有量之间的差额，会写成一笔日期为当前时间的补齐交易（标记为 `P`），从填充账户转入，排在 `balance` 之前。没有差额时不写交易。界面不写 `pad` 指令：`pad` 会为账户每种商品的下一条余额断言补齐，并会悄悄吸收你今天之后添加的交易。
- 你自己写的 `pad` 仍会为它之后、它从未补齐过的商品的余额断言补齐，并吸收该断言之前的交易。这样的余额断言会被拒绝，并指出需要先关闭的 `pad`：在该 `pad` 的后一天写一条该商品的余额断言。账户在 `pad` 之后才开始持有的商品也是如此。
- 已关闭或未开启的账户的余额断言，或从这样的账户填充，都会被拒绝，在张记账账本中也是如此。

被拒绝的请求不会写入任何内容，界面会显示原因。

张记账在填充的金额和配对上与 Beancount 有以下不同：

- 填充总是使账户精确等于断言金额，即使差额在明确写出的 `~` 容差之内，而 Beancount 此时不填充（见上文）。
- 只有对被填充账户本身的断言会使用这条 `pad`。Beancount 还会让子账户上的断言用掉父账户的 `pad`，之后父账户自己的断言就得不到补齐。
- 填充金额计入在它之前已补齐的每条断言的补齐。Beancount 计算父账户的填充时不计入其子账户的补齐，因此父账户的断言会差出这部分补齐而不成立。
- 张记账对同一天的指令先按时间排序，再按文件（按账本包含文件的顺序），再按行排序。Beancount 只按行号排序，不论文件，也没有时间。同一账户在不同文件中同一天的两条 `pad`，由张记账排在最后的那条填充，它可能不是 Beancount 使用的那条。在 Beancount 账本中，张记账忽略 `balance` 和 `pad` 的 `time` 元数据，因此同一文件中同一天的 `pad` 与 Beancount 的顺序相同。
- 填充按成本持有的商品时，张记账为它所服务的断言报告一条 `PadWithCost` 错误；Beancount 为每个按成本持有的批次各报告一次。

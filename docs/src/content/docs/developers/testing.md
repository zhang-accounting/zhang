Zhang has about 1,700 Rust tests and 150 web UI tests. They are organised in layers. Each fact is pinned once, at the lowest layer that owns it, and an upper layer checks it again only as part of a contract of its own: the journal lists the metadata of a posting, it does not prove again how that metadata attaches to the posting. This page says which layer owns what, where a new test goes, and the conventions the suites share.

## Layers

| Layer | Where | Owns | Fixtures |
| --- | --- | --- | --- |
| Unit | `#[cfg(test)] mod tests` next to the code | one function, stage or route handler in isolation | inline text only: no files, no fixtures, no `zhang-testkit` |
| Dialect | the `tests/` of `zhang-core` and of `extensions/beancount` | syntax, escaping, metadata attachment, flags and round trips of one format; the same scenarios run through both parsers with each dialect's own expectations | inline text, through `zhang_testkit::dialect` |
| Engine and pipeline | the `tests/` of `zhang-core` (booking, pads, balance checks, account lifecycle, the plugin host) and of `zhang-query` (BQL, the tables, the functions, `EXPLAIN`, the optimizer's equivalence checks) | the semantics | inline text, or a fixture ledger by name |
| Oracle | `zhang-query/tests` (beanquery, eight case sets under one harness) and the oracle directories of `extensions/beancount/tests` (beancount) | agreement with the reference tools, with every known difference listed as a deviation | generated case files over `integration-tests/fava-demo-ledger` and the oracle ledgers |
| API | the `tests/` of `zhang-server` | JSON shapes, status codes, error bodies, writes, ids, paging, authentication | scratch ledgers and the kit's `http` harness |
| Golden | the golden suites of `zhang-server/tests` | on every fixture ledger, the API answers what the engine, the store or an independent computation says; the ids of transactions stay what the golden file holds | `zhang_testkit::fixtures` |
| End to end | `zhang-cli` (one test per `integration-tests/` directory, plus process tests of the binary) and `frontend` (`pnpm test`) | the whole application | the fixture corpus |

The web UI tests are plain `node --test` files next to the code they test (`frontend/src/**/*.test.ts`).

## Where a new test goes

- **A parsing or writing rule of `.zhang` or `.bean`**: the dialect tests of that format's crate. A rule both formats share goes into the shared scenario, with one expectation per dialect.
- **A booking, pad, balance, account or plugin-host fact**: the `tests/` of `zhang-core`. **A BQL fact**: the `tests/` of `zhang-query`.
- **"beanquery answers X"**: a case in the beanquery case sets of `zhang-query/tests`, generated with `generate.py --set <set>`; never a hand-written expected value. **"beancount does X"**: the oracle directory of that behaviour in `extensions/beancount/tests`, regenerated by its `generate.py`.
- **An HTTP contract**: the `tests/` of `zhang-server`, at handler level (`respond(handler(state, ..).await)`); through the router (`send`, `call`) only when the middleware, the path encoding, the content type or an extractor's rejection is the point.
- **An invariant over every ledger**: a golden suite of `zhang-server/tests`, iterating `zhang_testkit::fixtures::every_fixture_ledger()`, split into parts so that no single test runs for more than a few seconds.
- **What a client of the budget system sees** (the budget pages' built-in queries, BQL over the budget tables, budget errors, the budget directives as each format writes them): a case in `zhang-server/tests/golden/budget_contract/`; see [The budget contract](#the-budget-contract).
- **A bug that needs a real ledger shape and an API answer**: a directory in `integration-tests/` with `main.zhang` (or `main.bean`, or both) and a `validations.json`. The end-to-end run checks the validations, and every golden suite loads the ledger from then on.
- **A web UI function**: `frontend/src/**/<name>.test.ts`.

## The budget contract

The cases of `zhang-server/tests/golden/budget_contract/` freeze what a client of the budget system sees, so that moving budgets into the official plugin (RFC #698) is checked against them: the answers of the built-in queries the budget pages and the app run, BQL over `#budgets`, `#budget_definitions`, `#budget_events` and the `budgets` of `#postings`, the ledger's errors with their ids, the budget directives as zhang and beancount write them, and what a round trip through each format changes. A case is a ledger and a `case.json` of requests; its golden files hold the answers. The cases read no Rust type of the budget system, so they keep their meaning whatever implements budgets. A behaviour that looks wrong is pinned with a `KNOWN-ISSUE:` note in `case.json`, which the golden file repeats, and is fixed in a change of its own, whose golden diff shows the fix.

When the migration changes a golden file, each difference is one of the allowed differences below, or a regression.

### Allowed differences for the migration

- The order in which the load reports errors at different places. Clients see the errors by file and position (`#errors`, `journals.errors`); the cases do not pin the load's own order across places.
- The text of messages: of the BQL limit errors (and the figures they quote, such as `1148412 months`), of parameter validation and of 404s, and the parser's text in a round trip's `load_error`. The status stays.
- Which filters make `#budgets` fail as generating too many rows: a 400 may become a correct 200, never a truncated or partial answer.
- The scale of a decimal, trailing zeros included (`10355.00` or `10355`): compare `number` by value. The digits of a value stay contract, such as the 28 significant digits of a conversion through an inverse rate. Only a value the answer types as a decimal has a scale: a `decimal` cell, or the number of an `amount`, a `position` or an `inventory` cell. A text cell or an error's meta that reads as a number stays exact.
- The order of the columns of a built-in query's result and of `SELECT *`, each column keeping its name and type.
- The order of the fields of a JSON object.

### Intended contract changes

Changes the migration makes on purpose, each in the change that makes it, with its golden diff:

- `provided_by` on every table and column of `GET /api/query/schema` (RFC #698 P1.3, §3.5): `"zhang:budget"` for `#budgets`, `#budget_events`, `#budget_definitions`, their columns and the `budgets` column of `postings`, `null` for the rest. In `schema.json` it is the field's only change: no name, type or order changes.

### What stays contract

Everything else, in particular:

- the order of rows: the natural order of a table read without `ORDER BY`, the order of budgets, of months, and of a month's events and postings;
- each error's kind, metas, span (file, start, end, line) and id, and the order of the errors at one place;
- every figure by value, every status, and every name and type of a column.

### The budget script against the native budgets

Until the bundled script `zhang:budget` (`plugins/budget/budget.lua`) is the only implementation of budgets (RFC #698 P3.3), zhang computes budgets natively, and a test switch chooses the implementation:

- `zhang_server::analysis::BudgetImpl` is `native`, `plugin` (the script, registered as a default plugin, in place of the native provider and checks) or `both`, and `load_options_for` loads a ledger with it. A build with the `budget-switch` feature of `zhang-server` (or of `zhang`, for the budget baseline) reads it from `ZHANG_BUDGET_IMPL` in every load the server makes; `both` loads with the script there, as a server serves one ledger. A build without the feature, every release, loads natively.
- `budget_contract_as_the_budget_script` runs every case of the contract with the script against the same golden files, ids and places of the errors included, and lists each difference with the rule above that allows it; any other difference fails it. With the native cases, it is the contract in `both` mode, in every test run.
- `the_budget_script_answers_the_reference_figures_on_every_ledger` checks the script's budget pages on every ledger of the repository against the independent computation of `budget_reference`, as `the_handlers_answer_the_reference_figures_on_every_ledger` checks the native ones. With `ZHANG_BUDGET_IMPL=plugin` (or `both`) every test of `budget_commodity`, its hand-worked ledgers included, loads with the script: `ZHANG_BUDGET_IMPL=plugin cargo nextest run -p zhang-server --test golden -E 'test(/budget_commodity/)'`.
- `zhang_testkit::budget_parity` is `both`: it loads a ledger natively and with the script, served as the server serves it, and compares the errors id-exact, the three budget tables, the `budgets` of `#postings`, the errors page and the budget pages' named queries. `budget_parity::the_bench_ledgers_answer_alike_both_ways` runs it on the budget baseline's two ledgers, on demand: `cargo nextest run --release -p zhang-server --test golden --run-ignored only -E 'test(the_bench_ledgers)'`.
- `the_budget_script_runs_as_many_queries_on_400_closed_budgets_as_on_200`, in every test run, loads generated ledgers of closed budgets with the script: it publishes, runs as many queries on 400 as on 200 (a few per budget commodity, whatever the number of budgets; an analysis runs at most 10,000), and answers as the native budgets do. `the_budget_script_reads_thousands_of_closed_budgets_in_a_few_queries` does so at 3,600, on demand. `the_budget_script_reads_budgets_of_every_month_on_one_account_by_account_and_month` loads 440 monthly budgets on 4 accounts, each in all 110 months, so that every posting is in the 110 budgets of its account: the script groups the postings of an account of so many budgets by account and month and reads each budget from its account's cells, in as many queries as for 120 such budgets, and answers as the native budgets do; `the_budget_script_reads_thousands_of_monthly_budgets_in_a_few_queries` does so on demand at 1,200 and 4,200 budgets (10 and 35 categories over 120 months). `the_budget_script_reads_more_groups_than_it_holds_by_ranges_of_months`, on demand, loads 404 budgets of an account each with postings in 100 months, more groups of a budget's postings of a month than the script reads at once: it reads them by ranges of months, which a census of the postings sizes. `the_budget_script_costs` measures the script's queries, their time, the analysis time and the peak memory of the load on such ledgers (`monthly<N>` for N categories of monthly budgets) and on the budget baseline's two, on demand: `cargo nextest run --release -p zhang-server --test golden --run-ignored only -E 'test(the_budget_script_costs)' --no-capture`. With `ZHANG_BUDGET_PARITY_BASELINE=<path of a budget.lua>`, every comparison of `budget_parity` and the fuzzer compares the bundled script with that one instead of the native budgets, such as a change of the script with the script of `main`.

#### The differential fuzzer

`budget_fuzz::budget_fuzz_finds_no_difference` compares the two on seeded generated ledgers (`zhang_testkit::budget_fuzz`): small ledgers, a function of their seed, that use every budget directive and break the budgets in every way the native code reports. A seed picks the timezone and the clock (a past one too), budgets defined late, twice or never, adds and transfers in other commodities, zero, negative or of many digits, to and from undefined budgets, closes at a time or twice, accounts of every type linked to several budgets and closed and opened again the same day, a budget only Income, Liabilities or Equity accounts (and maybe Assets) count toward, prices quoted either way, from a later month, zero or missing, shares sold from their lots (two lots at costs in two currencies in one posting too), a `pad`, postings at the very instant of a budget directive and on the day a budget is defined or closed, a month whose postings to a budget net to zero on a budget no price converts every posting of, an account whose `open` names a budget per month (each defined in its month and most closed at its end, maybe another account in some of them, and the account opened again in a month with the later ones only), date typos decades ahead or in 9999 (with enough budgets that the unbounded queries of `#budgets` fail as too large), a second file, and a `plugin "zhang:budget"` directive with options it does not have. On some seeds the timezone has daylight-saving changes and directives of every timed kind (postings, budget definitions, adds, transfers and closes, account opens and closes) fall on its change days between 01:00 and 03:59, at times the change skips, times it repeats and times around them; on some, amounts and prices have 9 to 28 decimals. Each ledger is compared on the errors id-exact, the three tables whole and by their wildcard, `#budgets` by year and up to a month, the `budgets` of `#postings` and its label fast path, and the five named queries for every month and budget.

- Every test run checks the seeds 1 to 40 (about 14 seconds on CI's 4 vCPU in a debug build), and asserts that together they exercise everything the generator can (the daylight-saving and long-decimal features included) and report every budget error.
- A difference fails the test with the seed, what it exercises, the first difference, and the smallest ledger found that still shows one (blocks of the ledger removed while a difference remains, for at most three minutes), written to `target/tmp/budget-fuzz/seed-<seed>/` too.
- The long run, the seeds 1 to 10,000, is the ignored test `budget_fuzz_long_run_finds_no_difference`, in release with the `budget-switch` feature: the `Budget fuzz` workflow runs it every night (and by hand, on any branch, with other seeds if asked), and `cargo budget-fuzz` (an alias in `.cargo/config.toml`) runs it on demand (in release, about 7 minutes on 4 cores; the workflow splits it in four shards of 2,500 seeds). When it fails, the workflow keeps the reproductions as an artifact.
- Other seeds run on demand, in release for speed: `ZHANG_BUDGET_FUZZ_SEEDS=1..=2000 cargo nextest run --release -p zhang-server --test golden -E 'test(budget_fuzz)'`, or one seed (`ZHANG_BUDGET_FUZZ_SEEDS=17`); `ZHANG_BUDGET_FUZZ_SEEDS` sets the seeds of `cargo budget-fuzz` too. `ZHANG_BUDGET_FUZZ_KEEP=1` writes every seed's ledger to `target/tmp/budget-fuzz/ledgers/`.
- The summary line counts the differences the rules above allow, by rule; the scale of a decimal is allowed only in a value the answer types as a decimal.

## Conventions

- Test names are sentences in `snake_case` that state the fact: `a_pad_books_the_difference_now`, `every_ledger_has_an_oracle`.
- A test never runs cargo, the network or a shell, except `zhang-server/tests/sdk_plugins.rs`, which builds the example plugins for `wasm32-unknown-unknown`. It needs the target installed; locally it is skipped without it, and left out with `-E 'not binary(sdk_plugins)'`.
- A test that runs for more than a few seconds is split by layout: slices of its inputs, each a test of its own, with one test asserting that the slices cover every input. The inputs themselves are never dropped.
- A golden file lies next to its test and is rewritten by running the test with `UPDATE_GOLDEN=1` (`zhang_testkit::golden`); the diff of the file is then what the reviewer reads. Oracle cases are only ever regenerated by their generator with the tool versions its `README.md` pins; a difference zhang keeps on purpose is a deviation entry there, not an edited expectation.
- Unit tests keep their own helpers. `zhang-testkit` is for `tests/` only: a library compiled with `cfg(test)` and the copy of the same library the kit links against are two different crates to the compiler, so their types do not match.
- Balance assertions in test ledgers are exact unless they are written with a `~` tolerance. In a `.zhang` file an indented line starting with `*` is a posting flag and one starting with `#` is a comment; `.bean` files follow beancount.
- The in-source tests of a crate must build without the features other crates turn on: `cargo test -p zhang-core` runs without the plugin runtime, which `zhang-server` enables.

## The test kit

`zhang-testkit` is a dev-dependency of the crates with integration tests. It loads and compares; what a test expects stays in the test.

| Need | Use |
| --- | --- |
| a ledger from text | `ledger::load_text`, `ledger::load_text_as` (a `.bean` main file), `ledger::load_text_at` (with a clock), `ledger::load_transformed` |
| a ledger on disk the test writes to or reloads | `ledger::Scratch` (`zhang`, `beancount`, `with_files`, `copy_of`; removed on drop) |
| the fava demo ledger | `fixtures::fava_demo` (loaded once per process) or `ledger::fava_demo_ledger` (a fresh load) |
| every ledger of `integration-tests/` and `examples/`, or one by name | `fixtures::every_fixture_ledger`, `fixtures::fixture_ledger`, `fixtures::fixture_dir` |
| the beancount oracle ledgers | `fixtures::oracle_ledgers` |
| a ledger of either format from a directory | `fixtures::load_dir` |
| a reproducible random source | `XorShift` |
| a household's ledger of any size from a seed, with budgets or without, the same byte for byte for a spec | `budget_ledger` |
| the dialect scenarios: random transactions and text layouts, where metadata landed | `dialect` |
| a golden file | `golden::assert_text`, `golden::assert_json` |
| a beanquery case set, run and compared under one set of rules (feature `query`) | `oracle` |
| a handler's `State`, a response as JSON, the server's router and requests through it (feature `server`) | `http` |

The crate's own documentation (`cargo doc -p zhang-testkit --features query,server --open`) lists every entry point.

## Running the suites

```bash
cargo nextest run                       # every Rust test
cargo nextest run -p zhang-query        # one crate
cargo nextest run -E 'test(journals)'   # tests whose name matches
cargo test --doc                        # the doctests (nextest does not run them)
cargo test -p zhang-core                # zhang-core alone, without the plugin runtime
cargo run --release -p zhang --example budget_baseline   # the budget baseline, not a test: see Budget Baseline
cd frontend && pnpm test                # the web UI
```

Running a single integration-test binary still works with `cargo test -p <crate> --test <binary>`. CI runs the Rust tests in three groups, `zhang-query`, `zhang-server` and the rest, each as `cargo nextest run` with a package filter, plus the doctests and `cargo test -p zhang-core` in the last group; a test's group is its package.

## Binary layout

A crate's integration tests are **one binary**: `tests/<name>/main.rs` declares the modules, one file per area under `tests/<name>/` (`zhang-core/tests/core/`, `zhang-server/tests/api/` and `tests/golden/`, and so on). Every integration-test binary links the crate and its few hundred dependency crates, so 74 of them cost half of a CI job's build phase, while the merged crate's extra front-end work was measured at well under a second. A test keeps a binary of its own only when it changes **process-global state**, which would leak into the tests running next to it: an environment variable read once per process (`zhang-server/tests/account_journal_limit.rs`), the working directory (`zhang-server/tests/document_cache.rs`), and `sdk_plugins.rs`, which runs cargo. Nextest runs every test in its own process either way, so the merge changes nothing about isolation at run time.

Add a test to the module that owns its area; add a module (a file under `tests/<name>/` and a `mod` line in `main.rs`) only for a new area; add a binary only for process-global state, and say why in its first doc comment.
